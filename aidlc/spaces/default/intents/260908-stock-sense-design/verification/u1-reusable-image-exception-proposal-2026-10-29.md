# U1 image-exception scope correction proposal — 2026-10-29

Status: **proposed; owner decision pending**. This document does not amend the approved security design, plan or protected-main ledger.

Rebuilding unchanged Kiota inputs produced image ID `sha256:f44db52549a696ff11da23fed2c9e6bce8bdc54d7e23825210e2c57ab0ddee13` in PR #68 and `sha256:ce072a1f577d9a636aa10f759d2276c64491c000e6561ed98506928e0d9e2806` in PR #69. A reusable exception cannot rely on a constant built-image ID. The official Kiota 1.36.1 package still bundles MessagePack 2.5.302, so a version bump alone has not been shown to remove the finding.

## Proposed rule

Use an owner-approved, time-limited exception for **only** `GHSA-qhrr-8q5h-9q3h` in `pkg:nuget/MessagePack@2.5.302` in the Kiota generator. Bind it to a stable, protected **Kiota execution fingerprint** rather than the complete candidate tree or a run-specific image ID. The fingerprint must cover the pinned base-image digests, Kiota 1.35.0 package SHA-256 `5e75f6adf161717be8d9f39eb596f93d52535e7b8cbcc00cffdcef3d0d3c3486`, Dockerfile/build script, exact `kiota generate` invocation and generated-input boundary, code that enforces input validation and offline references, container isolation and resource limits, scanner/evaluator code and dependency pins, and the trusted workflow/policy that executes those checks. Compute it from an explicit, reviewed Git path manifest. The protected-base policy must also compare the candidate's complete immutable Git path set against the approved execution/build/scan authority roots. A newly added helper, transitive dependency, Docker build input or executable path outside the manifest must fail closed, even when no existing listed file changed. A changed protected input invalidates the exception until a new assessment and owner approval.

On every PR, including docs-only PRs, build and identify the final validator and Kiota images; verify the Kiota version and nupkg bytes; inventory and scan each **actual run-specific image ID** with the pinned scanners and a current database; retain raw source-bound scan receipts; require the validator to have zero findings; and match the Kiota scan to exactly the one approved Medium finding. Because build metadata makes image IDs vary, compare a canonical final-runtime file manifest for the complete Kiota tool and probe payload, plus executable image configuration and package inventory, with an owner-reviewed protected-main baseline. The base runtime image is separately fixed by immutable digest. The canonical manifest must bind paths, modes and file hashes, ignoring only non-executable timestamps; any extra or changed executable content or package identity fails even if its scanner has no finding. Prove two independent hosted builds produce the same baseline before enabling reuse. If the runtime manifests differ, keep the exact-tree rule and return for design review. Any changed or additional finding, changed package, altered invocation/input handling, absent evidence, stale database, expired exception or fingerprint mismatch fails closed. The workflow and U2 policy must prevent candidate-controlled code from certifying its own exception. Ordinary changes outside the execution fingerprint can pass all three checks without a new ledger row. This includes future changes to canonical OpenAPI source content that still pass the existing input validation and offline-reference checks; the approval therefore accepts residual risk for new validated inputs under an unchanged execution boundary. A PR changing protected CI still needs the separate exact-base/head owner authorization and its own merge decision.

The approved `kiota generate` path uses no network, a read-only filesystem, a non-root user, a 2 GiB memory cap and a 120-second timeout. The proposed reusable exception expires no later than `2026-11-25T00:00:00Z`; an unidentified MessagePack deserialization path remains a denial-of-service risk. The earlier owner answer approved only one exact candidate tree and **does not authorize this broader rule**.
