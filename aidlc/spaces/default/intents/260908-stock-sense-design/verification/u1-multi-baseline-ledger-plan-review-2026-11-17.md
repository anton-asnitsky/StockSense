# U1 multi-baseline ledger plan and independent design review

Status: proposed implementation scope; no owner approval, risk acceptance, main change, merge, U1 acceptance or C01 release. Prepared by the independent process steward for the coordinator on 2026-11-17. No implementation was performed.

## Confirmed blockers

1. **Blocking — ledger cannot represent the three current candidates concurrently.** `tools/contracts/src/image-ledger.mjs:184` in the PR76 worktree requires every v1 row to match the current candidate tree, or every v2 row to match the current execution fingerprint and runtime. The three tree digests and execution fingerprints in [the candidate proposal](u1-r15-noble-disposition-proposal-2026-11-17.json) differ. Only the normalized runtime is common. Appending three groups without changing selection fails closed for every candidate. Runtime equality alone must not authorize a different verifier.
2. **Blocking — PR74 cannot consume v2 receipts.** Its `tools/contracts/src/sbom.mjs:40` validates only `stocksense-image-ledger-verification-v1`. PR75/76 contain the separate US8.7 v2 receipt change. A v2 ledger rollout must give PR74 the reviewed receipt compatibility prerequisite as well.
3. **Blocking — dispositions and protected main remain unauthorized.** The patched Noble plan explicitly excludes exceptions and protected-main changes. The 14 current rows remain proposals; eight OpenSSL rows have unresolved distro applicability proof, and no risk acceptance is inferred for the others. [The old question](../construction/contracts/code-generation/u1-v2-reusable-image-exception-questions.md) approves only one historical MessagePack row and preparation of its PR. Live GitHub PR73 is CLOSED, head `dbdfe87230b1b6fa334ea583df54ede082e9c673`, with no comments. Its body describes an obsolete runtime and execution fingerprint. It supplies no current authority.
4. **Blocking — publication dependency.** `fetchImageLedger` reads and hashes the immutable blob on live protected main, then rechecks main. A draft main PR or local simulated receipt cannot clear hosted U1. A separate exact merge decision remains required. Current main policy already supports exact base/head owner approval for protected paths, including the ledger; changing U2 policy or branch protection is unnecessary.

## Minimal proposed implementation

Obtain and verify a fresh protected implementation-plan receipt before changing the verifier. Keep v1 behavior unchanged. Extend existing v2 row selection by the exact pair `(executionFingerprint, runtimeManifestDigest)`; do not authorize by runtime alone, PR number, branch, or a wildcard. Preserve the existing row shape and v2 receipt shape. This is an explicit change to v2 multi-baseline semantics that must be named in the approved plan, not treated as a data-only correction.

Validate the complete ledger before selection: exact envelope/row/finding fields, supported images, digest syntax, known severity/fix state, identity/purl consistency, nonempty owner/rationale/control/approval reference, valid active timestamps, and no duplicate finding identity within a baseline. Reject malformed or expired rows even in other baselines, preserving the conservative whole-ledger validity rule. The same finding can appear once in each separately authorized baseline. Select only the exact matching pair and pass only that group's findings to the existing scan-to-disposition verifier. It must still reject missing, extra, duplicate or changed findings and fixed High/Critical issues. Compare disposed totals to the selected group, never to all ledger rows. A nonempty ledger with no matching group must fail; preserve the existing empty-ledger clean-image path.

Preserve source-revision, Git tree, full candidate-tree digest, actual image/SBOM/raw-scan binding and the live-main immutable-blob checks. The receipt continues to identify its exact execution/runtime pair and authoritative whole ledger blob; selected dispositions must be deterministically reconstructible from that blob and pair. Do not create a second ledger location or trust a PR-supplied file. Retain exclusion of only `security/image-exceptions.json` from candidate/execution binding so a ledger-only main publication is not circular. Do not exclude new verifier, test, helper or policy paths from the execution fingerprint.

Apply PR75's existing reviewed v2 SBOM receipt support to PR74 as a scoped prerequisite, without overwriting the US8.2 changes or combining story histories. Apply the shared selector to each branch after review. Candidate heads, test merges and execution fingerprints necessarily change; recompute all of them after the final code/test changes. Do not reuse today's U2 comments or execution digests for the updated heads.

## Required tests and verification

- Single-baseline v1 and v2 regression; empty clean ledger; three distinct valid v2 baseline groups selecting exactly one per candidate.
- Same runtime with different execution fingerprint must not borrow approval. Wrong runtime, no exact pair, changed protected path, changed candidate revision, missing manifest, stale raw scan and moved main all fail.
- Missing or extra selected finding, identity/version/purl/severity/fix-state drift, duplicate within a group, duplicate selected row, and fixed High/Critical finding all fail. Repeating the exact finding across different authorized groups succeeds only for the selected group.
- Malformed or expired unrelated group fails under the conservative whole-ledger rule. Invalid extra fields, unknown images and invalid timestamps fail before filtering.
- Combined SBOM verifies existing v1 receipts and v2 receipts for the exact source revision; altered execution/runtime receipt fields, extra receipt fields and wrong ledger schema fail. Verify on PR74 as well as PR75/76.
- With real retained artifacts, dry-run each proposed final group through the production verifier and combined SBOM path, including at least two independent builds with matching normalized runtime. Label these simulated main proofs; they are not protected receipts.
- Run relevant contracts tests, canonical package generation/validation, scans and secret checks; independently review final code and evidence. Follow all applicable hosted jobs on every new head and integration revision. The independent picomatch High finding remains separately blocking until supported remediation or its own permitted owner decision; this plan does not waive it.

## Separate protected-main proposal and owner boundaries

After final candidate scans and exact finding decisions, prepare a new isolated draft main PR containing only the reviewed ledger replacement and directly necessary evidence. Retire the obsolete MessagePack row only as part of that exact reviewed change. Use three explicit v2 groups if fingerprints still differ; authorize only the final measured pairs. Current scans have 14 rows per group, but the final row set must follow actual approved disposition evidence, not an assumed count. Approval references and dates must derive from real answers. Do not fill them with a planned approval.

The draft can be concrete and locally verified while merges remain prohibited, but it cannot make U1 green. Its protected-main U2 comment is independently `StockSense protected CI approval: <current-main-base40> <draft-head40>` from the repository owner. That approves protected path changes for those identities, not vulnerability acceptance or a merge. Main commit `8cce4f8040ad0767fca1b1ab14a00bb067a66b76` was inspected directly: its `tools/contracts/src/image-ledger.mjs` accepts only `stocksense-image-exceptions-v1` and requires every row to equal the candidate tree. It will reject the proposed v2 ledger. Before requesting any eventual merge, inspect the draft's own current checks and prepare a separately reviewed compatibility prerequisite and disposition of main's own runtime, or retain the publication block. A new selector alone cannot make main's different runtime match the three candidate groups. Do not propose bypassing failed required checks or silently importing the Bolt into main.

Implementation approval, finding-specific disposition approval, exact-head U2 approval and exact main-PR merge approval are distinct. Under the present no-merge instruction the legitimate endpoint is reviewed working-branch implementation plus a prepared proposal, with hosted U1 explicitly still blocked on main publication. No new owner decision is fabricated by this document.
