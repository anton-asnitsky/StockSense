# Demo Evidence Security and Quality Requirements

Unit: U13 Demo Evidence (`demo-evidence`)

## Boundary and trust model

U13 orchestrates reproducible validation and packages evidence. It owns no
business entity, tenant authority, infrastructure definition, production
credential, provider contract, or authoritative application data. It may call
only versioned, allowlisted deployment commands and supported application
interfaces. It shall never seed or repair state through direct database,
document-store, cache, vector-store, object-store, broker, or OpenSearch writes.

Evidence proves only what the recorded command, environment, revision, and
artifact demonstrate. File presence, a neighboring successful check, a healthy
dashboard, or prose cannot convert a failed, limited, rejected, unavailable,
not-run, missing, or expired result into a pass.

## Command and publication controls

- Manifests select a closed, versioned command profile and structured
  parameters. They cannot contain shell fragments, executable paths, redirection,
  substitutions, environment-variable expansion, or arbitrary network targets.
- The harness maps command IDs to checked-in implementations and invokes
  subprocesses with argument arrays, explicit working directories, allowlisted
  environment variables, deadlines, output caps, and cancellation.
- Trusted release manifests are signed with the approved CI identity. A clean
  local run may generate an ephemeral run key and publish its public key and
  trust class, but it cannot claim the trusted-release identity.
- Public evidence consists of compact manifests, Markdown summaries, measured
  tables, sanitized excerpts, contract/test reports, and small charts under a
  stable index. Raw sensitive or bulky artifacts never become a prerequisite
  for understanding whether a check passed.

## Explicit limitations

The targets describe a portfolio demonstration on the declared Docker Desktop
reference profile. They do not claim production availability, public-service
capacity, universal host support, accessibility certification, commercial
benefit, or cloud-provider equivalence. A locally signed reviewer run proves
integrity within that run; only trusted CI identity can produce trusted release
provenance.

## Required upstream contract actions

Before U13 code generation, the shared contract catalogue must publish C15 v2
with the delivery, backoff, digest, dead-letter-retention, and replay limits in
NFR7.1. C15 v1 remains explicitly legacy and its unresolved retry placeholder
cannot be interpreted as the approved policy.

U13 is the semantic owner of C19 v2: it defines the six-state result model,
required evidence metadata, state invariants, compatibility behavior, and
accepted examples. U1 is the packaging and validation owner: it publishes that
U13-owned definition in the shared contract catalogue, generates the canonical
JSON Schema and validator package, and makes them consumable by U2, U10, U11,
U12, CI, and the evidence index. The U13 implementation may begin only after
the U1 package validates U13's approved C19 v2 examples. Prior C19 v1 evidence
remains explicitly legacy; neither owner may reinterpret its three outcomes.
