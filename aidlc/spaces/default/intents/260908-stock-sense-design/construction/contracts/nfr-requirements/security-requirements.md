# Contracts Security Requirements

Unit: U1 Contracts (`contracts`)

Sources: confirmed `nfr-requirements-questions.md`; Contracts Functional Design; inception requirements NFR3, NFR5-NFR8, NFR10-NFR11, NFR13, and NFR15; and Contract Design C01/C15.

## Scope and ownership

U1 secures canonical contract sources, examples, validation, generation, compatibility evidence, and released contract packages. Each REST provider and message producer retains semantic ownership of its contract, authorization rules, error meanings, and evolution decisions. U1 may reject an unsafe or invalid candidate, but it cannot grant runtime authority, change provider semantics, or treat a valid schema as proof of runtime authorization, atomicity, delivery, or idempotency.

## Trust and threat boundaries

| Boundary | Trust assumption | Principal threats | Required boundary behavior |
| --- | --- | --- | --- |
| Public pull request to validation | Contributor code, schemas, examples, and configuration are untrusted | Secret theft, runner persistence, arbitrary code execution, SSRF, malicious references, oversized inputs, diagnostic leakage | Use a fresh GitHub-hosted runner with no deployment secrets or privileged credentials; disable arbitrary hooks; restrict references; sanitize diagnostics |
| Canonical repository to release job | Only a reviewed trusted revision may enter release packaging | Revision substitution, altered generated output, missing checks | Bind source revision and every input/output digest in the release manifest; reject missing or changed evidence |
| External schema/reference resolution | Network content is untrusted and mutable | SSRF, dependency substitution, nondeterministic validation | Vendor references or resolve only an explicit allowlist with integrity pins; deny undeclared network resolution |
| Toolchain to generated output | Validators and generators execute repository-controlled inputs | Compromised dependency, vulnerable tool, nondeterministic or manually edited output | Exact-version pins, locked installs, SBOM, vulnerability and secret gates, clean regeneration, output digest comparison |
| Released package to consumer | Package transport and storage are not sufficient provenance | Tampering, wrong revision, forged package | Verify SHA-256 manifest and GitHub artifact attestation before use; fail closed on any mismatch |
| Contract metadata to runtime service | Tenant, actor, scope, and placement fields are context, not authority | Authority confusion, cross-tenant access, stale placement | Validate required context and negative fixtures while leaving runtime authorization and effects to the provider |

## Detailed requirements

| ID | Requirement | Measurable acceptance and evidence | Failure behavior |
| --- | --- | --- | --- |
| NFR3.1 | Every applicable HTTP, job, and event contract shall carry retailer, actor or workload, placement-generation, correlation, causation, and idempotency context without representing client-supplied context as authority. | Policy checks pass positive fixtures and reject fixtures with missing retailer context, identifier substitution, missing actor/workload, stale placement generation, and absent idempotency identity. Evidence names the contract, fixture, rule, and immutable revision. | The validation run fails; no package containing the candidate may be released. Runtime tenant isolation remains an owning-unit obligation. |
| NFR5.1 | Browser-facing contracts shall preserve the BFF/session/CSRF boundary, and machine-facing contracts shall declare narrow issuer, audience, scope, and job-authority expectations. U1 shall never mint credentials or infer a human role for a machine caller. | Contract policy checks reject browser tokens exposed to client code, absent CSRF requirements on mutations, overbroad machine scopes/audiences, and machine approval authority. Provider-owned negative runtime tests remain required separately. | Reject the candidate with the violated authority rule; schema conformance cannot override a provider denial. |
| NFR6.1 | Secrets, credentials, tokens, signing material, raw supplier documents, full prompts, and hidden reasoning shall not appear in canonical packages, generated output, manifests, attestations, diagnostics, or logs. | Secret scanning reports zero unresolved credential findings for every pull request and release package. Test fixtures use documented non-secret placeholders. | Fail the check. A suspected live credential is removed and rotated before rerun; it is not accepted by exception. |
| NFR6.2 | Untrusted validation shall not obtain deployment secrets, owner credentials, write-capable release tokens, self-hosted runner access, unrestricted network reference resolution, or arbitrary generator hooks. | A CI configuration test proves the public-PR job uses a GitHub-hosted runner, has read-only minimum permissions, receives no deployment environment, vendors or integrity-pins allowed references, and runs with hooks/plugins disabled unless explicitly allowlisted. | Deny the privileged path and fail the CI configuration check before executing contract tools. |
| NFR7.1 | AsyncAPI policies shall require distinct job/event identities, durable publication intent, confirms, transactional outbox/inbox boundaries, acknowledgement after commit, idempotent consumption, bounded retry, DLQ, and audited replay, without claiming exactly-once transport. | Positive and negative fixtures cover `inventory-import.requested`, one mutually exclusive terminal outcome, one authoritative audit event, duplicate delivery, exhausted retry, and replay metadata. Each later message boundary supplies equivalent provider-owned evidence. | Fail the reliability-policy check and identify the missing or unsupported claim; runtime delivery remains unproven until the producer/consumer tests pass. |
| NFR7.3 | C15 v2 shall bind each producer through the authenticated RabbitMQ connection and a workload identity whose issuer, audience, scope, and producer/message-type authorization are declared by the owning producer. Its common envelope shall include immutable message/event identity, producer identity, retailer and placement context, correlation and causation identities, schema version, canonical-payload SHA-256 digest, occurred-at time, and idempotency identity; the encoded envelope shall not exceed 64 KiB. Delivery uses five total attempts with exponential backoff bounded from one to 30 seconds, seven-day dead-letter retention, and audited replay batches of at most 100 with one active replay per queue. | AsyncAPI and transport-policy fixtures reject wrong connection identity, issuer, audience, scope, producer/message binding, digest, retailer, placement, schema, or an encoded envelope above 65,536 bytes. Failure fixtures prove attempts are numbered 1-5, the fifth failure dead-letters, replay retains the original identity/digest, and replay remains authorized and idempotent. | Reject before retention or business effect when identity, digest, schema, or size is invalid. After the fifth eligible transport failure, dead-letter visibly; never manufacture a new business operation or treat replay as new authority. |
| NFR8.1 | Every included OpenAPI, AsyncAPI, shared schema, reference, example, compatibility result, and required consumer-local generation profile shall pass the pinned validation suite. | The immutable validation result records all applicable checks. Valid examples pass, declared invalid examples fail for the declared reason, and no required result is missing or not run. | Mark the run failed and block the corresponding integration or release. |
| NFR8.2 | Ownership metadata shall identify the provider or producer as semantic owner and U1 only as package, validation, compatibility, and publication-governance owner. | A package-wide ownership check resolves exactly one semantic owner for every document and rejects conflicting or missing ownership. | Reject the candidate; U1 shall not repair it by silently changing semantics. |
| NFR8.11 | C18 v2 shall provide a browser-safe same-origin API with `/signin-oidc`, a no-store CSRF bootstrap/rotation representation, CSRF on every mutation, and payload-bound idempotency on every logical command, including retailer selection, imports, manual inventory review, purchasing transitions and receipts, and assistant turns. It shall replace dashboard HTTP `206` with HTTP `200` plus typed aggregate and section states; define provider-owned operation status and reconciliation, bounded assistant SSE and snapshot recovery, bounded audit-query pagination/freshness, evidence retrieval, stable RFC 9457 problems, and response-size limits. | OpenAPI fixtures generate browser/BFF clients and cover CSRF bootstrap and rotation at login, reauthentication, session renewal, and retailer-context change; missing/forged/stale CSRF; missing/reused/changed-payload idempotency keys; complete/partial/unavailable dashboards; operation reconciliation; SSE resume/expired cursor snapshot; bounded audit queries; and oversized responses. No mutating operation may omit the applicable headers. | Reject the contract or request before provider invocation. Never emit HTTP `206` for the dashboard, retry an uncertain mutation automatically, expose provider exceptions, or infer completion from a lost response. |
| NFR10.1 | Public diagnostics shall be bounded and sanitized: no secret or excluded payload content, no unrestricted source dumps, and no attacker-controlled terminal or annotation injection. | Sanitization tests cover tokens, credentials, raw documents, prompt content, control characters, absolute runner paths, and oversized findings. Published diagnostics retain rule ID, relative artifact path, bounded location, severity, and remediation summary. | Suppress unsafe detail, retain the complete result only in an access-controlled artifact when permitted, and fail the run if a safe actionable diagnostic cannot be produced. |
| NFR11.1 | A reviewer shall reproduce validation and generation from a clean checkout without owner credentials, cached tools, models, or GPU access. | A clean hosted run installs exact locked versions, verifies tool checksums where available, validates the initial fixture, regenerates all required outputs, and records source/configuration/output digests and elapsed results. | Mark reproducibility failed; cached local success or fixture-only evidence cannot substitute. |
| NFR13.1 | Public pull-request validation and trusted release/deployment execution shall be separate trust paths. Public PR code shall never execute on the isolated self-hosted deployment runner. | CI policy inspection and a synthetic public-PR test show the untrusted job remains hosted and unprivileged; the trusted release job verifies an immutable reviewed revision before packaging. | Block the workflow and report a trust-boundary configuration failure. |
| NFR13.2 | Contract validation and generation dependencies shall produce a machine-readable SBOM and be scanned for known vulnerabilities. Known Critical or High findings with a fix available block acceptance; every accepted non-secret finding requires a recorded owner, rationale, scope, and future expiry. | The SBOM identifies direct and transitive tool dependencies and versions. CI retains scanner output; verifies each exception is finding-specific, unexpired, and scoped; and fails expired or missing exceptions. | Fail the gate. Integrity failures and secret findings cannot be waived; expired exceptions fail closed. |
| NFR13.3 | Every released package shall include a SHA-256 manifest and GitHub artifact attestation bound to the trusted repository revision and release workflow. | Verification from a clean consumer environment proves the attestation identity and subject digest, then verifies the manifest entries for revision, canonical sources, generator identities/versions, configurations, generated outputs, SBOM, and validation result. | Reject and quarantine the package on missing evidence, identity mismatch, digest mismatch, or unverifiable attestation; no exception converts it to trusted. |
| NFR15.1 | Security and supply-chain evidence shall link stable inception NFR IDs, contract/rule IDs, source revision, package version, check identities, actual outcomes, and artifact digests. | An automated referential-integrity check resolves every recorded ID and digest and preserves passed, failed, limited, rejected, waived, and not-run outcomes. | Mark evidence incomplete and prohibit release or complete-coverage claims. |
| NFR15.2 | Security exceptions shall remain explicit, narrow, reviewable, and time bounded. | Each exception records finding ID, affected package/tool/version, rationale, compensating control, owner, approval reference, creation time, and expiry; CI proves the exception matches the current finding and is not expired. | A stale, broad, unmatched, or ownerless exception is ignored and the underlying finding blocks the change. |
| NFR15.5 | C19 v2 shall use exactly one check outcome from `passed`, `failed`, `limited`, `rejected`, `unavailable`, or `not-run`. U13 Demo Evidence is the semantic owner of the evidence schema and compatibility meaning; U1 owns canonical packaging, validation, examples, compatibility checks, and generated consumer artifacts. | Schema and ownership tests require a stable reason code, expected and actual result, requirement/story/test IDs, immutable revision, environment fingerprint, start/end times, allowlisted command profile and structured arguments, artifact checksums, and limitations. They reject unknown outcomes, contradictory success fields, mutable revisions, unresolved IDs, and ownership that assigns evidence semantics to U1. | Reject the manifest and prohibit a success claim. Preserve C19 v1 as explicitly legacy three-state evidence; do not reinterpret its outcomes as C19 v2. |

## Binding construction contract delta

The NFR Requirements stage fixes the following additive or major-version changes
for all downstream NFR Design and implementation work. They supersede unresolved
or conflicting placeholders in the inception contract summary without changing
the owning provider's business authority:

- **C15 v2:** NFR7.3 is the canonical delivery/security profile. C15 v1 may be
  consumed only during one tagged-release compatibility window and only when an
  adapter supplies and verifies the missing producer binding and digest before
  retention. Oversized or unverifiable v1 messages are rejected; the window does
  not weaken five-attempt delivery or dead-letter/replay controls.
- **C18 v2:** `/signin-oidc` is the callback. A same-origin `GET` session/CSRF
  bootstrap returns the opaque synchronizer token in a no-store response; the
  token stays in browser memory and rotates on login, reauthentication, session
  renewal, and retailer-context change. Every mutation requires
  `X-CSRF-Token`; every logical command additionally requires one UUID
  `Idempotency-Key` bound to actor, session, retailer, operation, expected
  version, and canonical request hash. Dashboard aggregation uses HTTP `200`
  with `complete` or `partial` aggregate state and per-section `fresh`, `stale`,
  `unavailable`, or `forbidden` state. Provider-owned operation status, SSE
  resume/snapshot, bounded audit queries, evidence retrieval, response limits,
  and stable problems are mandatory generated-client surfaces.
- **C19 v2:** NFR15.5 is the canonical six-state evidence contract. U13 owns
  semantics and proposes versions; U1 packages, validates, compatibility-checks,
  and generates consumers. C19 v1 remains readable as legacy evidence and is
  never silently upgraded.

## Required security evidence

- Immutable validation result and sanitized findings for the evaluated revision.
- Secret-scan result, machine-readable SBOM, vulnerability report, and exception records where applicable.
- SHA-256 release manifest and GitHub artifact attestation, plus a clean-environment verification result.
- Positive and negative tenant/authority, reference-resolution, hook-disablement, diagnostic-sanitization, and public-PR-isolation fixtures.
- Provider-owned runtime evidence for authorization, transactionality, delivery, deduplication, and side effects; U1 evidence only establishes contract requirements.
- Versioned C15 v2, C18 v2, and C19 v2 schemas, positive/negative examples, compatibility reports, ownership metadata, and generated-client drift results matching the binding construction delta.

## Explicit limitations

- The exact SBOM generator, vulnerability scanner, secret scanner, GitHub attestation action, and SBOM format are not yet selected. Their implementations must be exactly pinned and satisfy the requirements above before the CI design is approved.
- No maximum schema size, reference depth, evaluation time, diagnostic count, or generator resource budget is confirmed. Until NFR Design sets bounded values, untrusted validation must use finite runner-level time, memory, output, and network limits and record any limit-triggered result as failed or limited, never passed.
- GitHub artifact attestation proves the configured workflow produced the artifact for the declared subject; it does not prove provider semantics or runtime behavior.
- U1 does not provide a runtime authorization service, secrets service, broker, database control, deployment permission, or production release authority.
